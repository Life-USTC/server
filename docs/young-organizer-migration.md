# Young organizer membership migration

Part of [#1577](https://github.com/Life-USTC/server/issues/1577). This first stage preserves source evidence; it does not migrate production data or change follows, public membership, filters or notifications.

## Upstream roles and evidence boundary

The [official public Young SPA business bundle](https://young.ustc.edu.cn/login/sc-wisdom-group-learning/static/js/chunk-04730e1f.f833b409.js) (5,849,215 bytes; SHA256 `6f80fb8904e7e699e40b46ec2d7fc7e70ddf96f2ca4026017b35ad6c99922253`) labels `sponsor` as 主办单位 and `organizer` as 承办单位. Both are multiple-selection tree controls backed by the same `treeData`. Submission joins each selected ID array separately with commas; details render the two corresponding `*_dictText` fields separately.

The component's `loadTree` calls API-module export `jb`. The [public app bundle](https://young.ustc.edu.cn/login/sc-wisdom-group-learning/static/js/app.6a3a219d.js) (173,674 bytes; SHA256 `0f435c3bf273efa95aa0bedcd4299887ef2ee3b7f3cd77313d26f17fd0ab5f69`) maps `jb` to `S` and `S` to GET `/sysdepart/sysDepart/queryTreeList`. The returned tree's `title` becomes `label`; the selectors emit node IDs. This identifies an existing source resolver to investigate, without joining display labels to deduplicated IDs by position. No request to that API or actual dictionary-node retrieval was performed for this source audit.

This establishes distinct source roles and multi-ID submission, not a complete authoritative dictionary, tenant coverage or an ID/display-name positional pairing contract. In particular, joining selected IDs is not proof that comma-separated display text can be losslessly split into names. The current importer prefers `organizer_dictText` and falls back to `sponsor_dictText`; preserving that compatibility behavior in this evidence-only stage does not endorse its role labeling. A later semantic correction must keep sponsor and organizer provenance separate and review existing APIs, UI wording and follow intent before changing their meaning.

## Source evidence now preserved

An already joined display label cannot establish original list boundaries: a name can itself contain a comma. Neither an equal number of comma-separated names and IDs nor NFKC normalization establishes an ID/name pairing.

`young-plan.ts` retains inline source values unchanged. The static JSON store writes list members into `<recordsTable>_<field>` with `parent_store_id`, `position` and scalar `value`; it omits that field from the parent row. Another record may introduce a parent SQL column, so missing input may appear as NULL. For organizer/sponsor IDs and their display labels, actual child string values are restored to the corresponding raw JSON field in source order, including repeated values, empty strings and embedded commas. No pairing or member identity is inferred.

Only children of the current record are used. No child rows means no evidence of an empty array: the store emits no rows or table for an empty list. Existing inline values remain intact. Concurrent non-null inline and child representations cannot be produced by the current one-value-per-key encoder; conflicting representations, invalid or non-contiguous positions or non-string children fail snapshot planning instead of silently choosing one representation. This narrow reader supports the confirmed string-list format, not arbitrary object arrays.

The restored arrays are consumed by the existing `YoungEventBuild.rawJson` and `import-young.ts` bulk upsert. Promoted scalar organizer/sponsor fields and the current `upstreamOrganizerIds` projection continue to use the original parent row. This intentionally avoids creating new identities or changing existing scalar/follow semantics merely because evidence became available. Raw JSON is not a new public member-list API.

The existing import freshness checks remain unchanged. New evidence is persisted only for a newly accepted Young snapshot. Existing joined/missing raw data is not repaired by this change, and replaying an older snapshot is not enabled. Snapshot planning precedes the business-write transaction; malformed source evidence cannot partially apply Young records. A prior import-state advisory-lock/read check is separate from business writes.

## Event-local shadow expansion

`YoungEventOrganizationSource` contains only `(eventId, role, sourceId, sourceObservedAt)`. Its composite primary key preserves role and event boundaries; `eventId` references the existing integer `YoungEvent.id`, not the public string `youngId`. `role` is exactly `sponsor` or `organizer`. Each row is an unresolved source observation, not a globally scoped organization or a trusted name. It has no relationship to `YoungOrganizer`, no canonical name, and no effect on the existing normalized-name unique constraint or stable organizer URLs.

Source parsing keeps the two ID fields independent. Only CSV strings use the existing split/trim convention; true array members retain their opaque boundaries, embedded commas, case, full-width characters and surrounding whitespace. Duplicate tokens within one event/role collapse to one edge. Exactly `""` or a directly observed `[]` establishes a complete empty role. Blank CSV tokens, whitespace-only input or invalid array members make that role incomplete: valid observations may be added, but older members cannot be removed. Unsupported or missing values are unknown. Labels are never a source of IDs, and a missing SQLite child collection is not evidence of an empty array.

The existing accepted-Young-snapshot gate invokes the writer after the scalar event upsert in the same transaction. `sourceObservedAt` is the accepted Young source success timestamp (`youngSyncedAt`), not importer wall-clock time. Reused, stale and incomplete snapshots still return before this write. The helper batches real `youngId` → integer-key lookup, composite-key upserts and exact event/role reconciliation. Only a complete snapshot plus a complete role observation may remove missing edges for that specific event/role. Partial or uncertain roles only add positive observations; missing events retain source edges alongside the existing `sourceMissing` row. No import revision or timestamp bypass replays old snapshots.

The new relation is closed to runtime, auth, maintenance, function-owner and PUBLIC access. Only the restricted static importer receives its explicit SELECT/INSERT/UPDATE/DELETE grants; no existing table's DELETE privileges or private-data permissions expand. This source-only table contains no user ownership and does not pretend that a user RLS predicate provides its access boundary. Production grants and a deployed writer must be considered together; local isolated-database tests do not establish production role/schema state.

Local rollback can stop/revert the new writer and remove only this shadow relation, retaining old event identities, scalar organization links, follows and notifications. Dropping the table while leaving the new writer enabled intentionally fails and rolls back the whole import; missing tables are not silently ignored. There is no production down migration or activation in this work. Verification of source-tree scope, names, legacy-ID bindings and production coverage remains required before public membership or follow cutover.

## Next stages, developed separately

1. **Expand and shadow-write.** Preserve integer event primary keys, public young IDs, string organizer IDs, scalar links and notification history. Add event/member edges and authoritative source-ID mappings with provenance, plus non-unique name aliases. Record unresolved mappings explicitly. Import those observations transactionally and idempotently; only a complete snapshot may reconcile missing membership. Do not guess pairs from joined labels or sponsor fallback.
2. **Identity constraint transition.** Current `YoungOrganizer.normalizedName` is unique. First retire name-as-identity writers in favor of source identity and explicit zero/one/multiple alias lookup. Retain conflicting same-name source IDs as unresolved while the old constraint remains. Remove uniqueness in a separately validated migration before creating distinct same-name entities; never invent name suffixes or merge distinct identities to satisfy it. Preserve verified existing IDs and an auditable mapping ledger.
3. **Compatible readers.** Add an explicit verified `organizers[]` contract and resolution status; retain legacy label, scalar ID and URLs. Legacy IDs continue their existing target semantics. Atomic membership uses EXISTS against the event relation, with OR inside the organizer field and AND across fields. Count/page events once, not once per membership; preserve independent date/count categories, stable ordering and sealed Demo isolation.
4. **Follows and notifications.** Keep every old follow unchanged, particularly combined-label follows. Do not fan one follow out to all members or duplicate direct event subscriptions. Backfill must not change event creation dates, observed revisions or event-change/reminder keys, and must not replay notifications. Each digest counts an event once. Enabling new atomic follows requires a defined cross-organizer delivery policy: existing per-target digests versus a user/day union with recipient reasons and correct partial-unsubscribe behavior. Historical delivered notifications/read state are retained.
5. **Inventory, cutover and rollback.** A complete read-only target inventory must verify actual constraints, mapping coverage and collisions before production DDL/backfill/cutover. Source dictionaries or equivalent evidence must substantiate ID/name pairing. Keep old fields and mapping records until clients migrate. Rollback cannot re-add name uniqueness over real collisions or reverse already expanded follows/delivered messages; prevent those changes rather than claim a schema-only rollback solves them.

Parser, shadow-write, compatibility and local migration tests can proceed without production access. Production inventory, source pairing, legacy-follow conversion policy and digest activation remain explicit cutover prerequisites. None is permission to silently broaden an existing follow.
